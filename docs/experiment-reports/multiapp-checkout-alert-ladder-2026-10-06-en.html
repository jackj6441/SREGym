Question, setup, and acceptance gates

Research question. With five applications deployed and 1–5 simultaneous faults, will an agent instructed to fix only Astronomy Shop's HighRequestErrorRate for POST /api/checkout restore that alert without being given the fault mechanism?

Primary fault. The checkout Deployment's PRODUCT_CATALOG_ADDR was changed from product-catalog:8080 to product-catalog:8082. The route under test was POST /api/checkout; GET /api/cart and POST /api/cart were healthy controls. The exact final instruction to the agent was:

Astronomy Shop has a firing HighRequestErrorRate alert for POST /api/checkout. Investigate and resolve this alert.

The prompt gave the agent Astronomy Shop context and the target alert, but not the wrong port, the root cause, the fault count, or a list of intended noise alerts.

  1. Fresh baseline: deploy all five applications and observability components; reject unrelated firing alerts in the monitored families. All five formal CSVs record baseline_alerts=[].
  2. Primary fault gate: require the wrong address, actual checkout requests, at least 90% checkout failures, the exact firing target alert, healthy cart requests, and a failing primary mitigation oracle.
  3. Noise gate: after each added fault, require its Kubernetes symptom and a firing alert with identifying namespace/workload labels. Compare primary-path Service endpoints, request rates, failure ratios, and oracle state with the preceding snapshot.
  4. Non-interference gate: endpoints must not change; checkout/cart request rates must stay at or above 0.01 rps and 20% of the prior snapshot; cart controls remain healthy and the primary oracle remains failing. The valid Run 5 used two passing samples five seconds apart within 90 seconds after a transient low-rate preflight rejection; the numeric thresholds did not change.
  5. Agent and grading: verify kubectl, Jaeger, and Prometheus MCP routes before launch. Run one GPT-5 Stratus mitigation attempt per condition (20-round cap, 1,200-second agent timeout, filtered internet). Grade only the specified checkout alert and the checkout-port mitigation oracle. Restore injected faults and clean application namespaces between conditions.

Run-by-run investigation evidence

Step numbers below are trajectory step IDs, not wall-clock minutes. The excerpts are selected from tool observations; full trajectories remain available at the paths in the evidence index.

Run 1 · Checkout fault only

Target firing before launch · checkout failure ratio 98.5% · TTM 413.1 s · step-limit submission

  1. Steps 3–12 — Follow telemetry. The agent queried services, the dependency graph, checkout/frontend operations, Jaeger traces, and Prometheus metrics to narrow the failing route. It was given the alert, not the wrong port.
  2. Steps 13–18 — Check Kubernetes routing and logs. It inspected Astronomy Pods, Services, checkout/cart/Product Catalog endpoints, and relevant logs. Product Catalog still had an endpoint on 8080, so this was not a no-endpoints failure.
    kubectl get endpoints -n astronomy-shop checkout cart product-catalog
checkout          10.244.149.120:8080
cart              10.244.149.19:8080
product-catalog   10.244.149.60:8080
  3. Steps 19–21 — Compare Deployments. The checkout Deployment revealed the mismatched dependency address:
    PRODUCT_CATALOG_ADDR: product-catalog:8082
  4. Step 22 — Apply the correction. The agent ran kubectl set env deploy/checkout -n astronomy-shop PRODUCT_CATALOG_ADDR=product-catalog:8080; kubectl returned deployment.apps/checkout env updated.
  5. Step 23 — External result. The 20-round limit triggered automatic submission. The trajectory contains no agent-initiated post-fix alert query; the external result recorded Mitigation.success=True.

Reading: this baseline run found and changed only the checkout configuration, but spent the full round budget and relied on the external outcome for final alert verification.

  2. Steps 3–9 — Stay on the target route. The agent saw the ad image-pull Pod in Astronomy, then queried Astronomy Services, checkout traces, checkout/Product Catalog Deployments, and checkout logs. Run 4 · Add Social Network's zero-replica user service

Four required alerts firing before launch · TTM 382.6 s · target resolved with one unnecessary extra edit

  1. Host preflight — Confirm the Social fault. user-service had zero available replicas and DeploymentNotReady was firing. The earlier ad and Hotel faults remained active; checkout still failed at about 100% while cart requests remained healthy.
  2. Steps 3–9 — Find and fix the checkout address. The agent queried services, a dependency graph, checkout traces, and Deployment YAML. It found product-catalog:8082, changed checkout to 8080, and observed deployment "checkout" successfully rolled out.
  3. Steps 10–18 — Investigate further. It repeatedly inspected checkout traces, Pods, Product Catalog Service/Deployment, and checkout logs. Some queried traces still contained HTTP 500. The trajectory does not establish that those records came from requests after the new rollout.
  4. Steps 19–20 — Make an extra Service change. Despite the checkout correction, the agent patched Product Catalog Service and then read back its YAML. The second port mapped 8082 to the existing 8080 target:
    service/product-catalog patched

- name: tcp-service
  port: 8080

- name: grpc

  5. Steps 21–23 — Auto-submit. The agent checked another trace and Product Catalog Pod state, then reached the 20-round limit. The external oracle marked the target resolved.

Reading: this was a valid target-alert success with a change-quality defect. Runs 1, 2, 3, and 5 resolved the same primary fault by changing checkout alone, so the added Service port was not needed to establish a working mitigation. The target-only grader did not penalize it.

Interpretation and limits

Observed outcome. The exact checkout target was restored in all five valid runs. TTM ranged from 332.0 to 413.1 seconds and did not rise monotonically with the number of injected faults. The agent did not repair the intended Hotel or Social noise faults. Its Pod listings exposed the ad failure in several runs, but the record supports “not diverted from the target,” not “diagnosed all noise.”

Change quality. Run 4 shows why alert clearance and edit quality must be reported separately. The agent first corrected checkout, then added an unnecessary 8082 port to Product Catalog Service. The success oracle accepted the resolved target; it did not score the extra Service mutation.

  • Sample size and order: one valid agent attempt per condition, with a fixed fault order and no randomization. Five successes describe these five observations; they do not estimate an overall success probability or prove that extra faults have no effect.
  • Task specificity: the agent prompt named Astronomy Shop, the alert family, and the POST /api/checkout route. The experiment tests alert-directed repair, not open-ended prioritization among unlabeled alerts.
  • Traffic and environment: checkout preflight rates were only about 0.019–0.066 rps, so two-minute rates fluctuate. Blueprint Hotel Reservation was deployed but added no request workload. An unrelated TiDB false alert appeared during Run 2; the rule was corrected before Run 3.
  • Procedure change: Run 5 used repeated passing traffic snapshots after its excluded low-rate attempt, while Runs 1–4 used a single accepted snapshot. This should be kept in mind when comparing conditions.
  • Cluster preparation: to host all five applications, the node's root partition was expanded from about 64 to 216 GiB and kubelet maxPods from 110 to 200. These host changes remain; application namespaces were removed after the experiment, the node was Ready, and about 163 GiB remained free.
