Checkout alert investigation
Six-run debugging report

A matched control/noise experiment asked a GPT-5 mitigation agent to resolve the firing HighRequestErrorRate for POST /api/checkout. This report follows the agent's decisions in each run, with additional detail for the three noise runs.

Experiment date: 2026-10-03Control: 3 runsAd-image noise: 3 runsMitigation onlyStratus agent: gpt-5

Observed result. The target alert and the benchmark's Product Catalog mitigation oracle passed in all six runs. Every agent changed checkout's Product Catalog address back to product-catalog:8080. The noise case kept the original ad Pod serving while a new ad Pod failed image pull and raised a separate PodStatusError.

Important exceptions. Noise run 1 added an unnecessary 8082 port to the Product Catalog Service after confirming that the new checkout Pod already had the correct 8080 address. In noise run 3, the agent's last alert query still showed firing; the driver verified clearance later, after the alert's rate window caught up.

1. Setup and criteria

The starting fault changed checkout's PRODUCT_CATALOG_ADDR to product-catalog:8082. The Product Catalog Service exposes port 8080. Checkout's GetProduct gRPC calls timed out on 8082, causing failures on POST /api/checkout. The agent's initial prompt named the application and the firing checkout alert, but disclosed neither this root cause nor the ad fault.

The noise arm applied astronomy-ad-image: a nonexistent image produced a new ad Pod in ImagePullBackOff while the previous Ready ad Pod remained available. The profile waited for the independent PodStatusError and checked live checkout, cart, and ad traffic plus Service endpoints before the agent started.

The driver judged only the assigned HighRequestErrorRate with labels namespace=astronomy-shop, method=POST, and name=/api/checkout. After the agent finished, it allowed up to 240 seconds for recovery and required 120 seconds without the matching alert firing. The benchmark also ran its Product Catalog dependency oracle. A different alert remaining active did not fail the target check.

Six fresh deployments ran in this order: control 1, noise 1, control 2, noise 2, control 3, noise 3. All used the full application profile, Stratus gpt-5, judge gpt-4o-mini, and an 1800-second agent timeout. A prior calibration run was stopped and excluded from these results.

3. Noise isolation before agent start

Each noise preflight observed a firing checkout alert, a failing checkout dependency, and real checkout, cart, and ad requests. The checkout failure ratio stayed near 1.0; both cart endpoints had zero observed failures before and after injection. Recorded endpoint sets for checkout, Product Catalog, frontend, cart, and ad were unchanged.

4. Detailed noise-run traces

Noise run 1 · 1003_2023

176.700 s · Target pass · Main oracle pass · Extra Service patch

The agent encountered the bad ad Pod during its general Pod check but pursued the checkout failure. After correcting checkout and confirming its new Pod used port 8080, it made an unnecessary second change to the Product Catalog Service.

  1. Preflight established two independent faults

    The new ad Pod was waiting with ImagePullBackOff; the old ad Pod remained Ready. Checkout's failure ratio was about 1.000 before and 1.001 after noise injection, with the target alert still firing and Service endpoints unchanged.

  2. Trace exposed the checkout failure S3–S4

    get_services listed the application; get_traces(service="checkout", last_n_minutes=30) returned a Product Catalog GetProduct client span timing out while dialing port 8082.

    ProductCatalogService/GetProduct → dial tcp ...:8082: i/o timeout

  3. Pod inspection exposed, but did not redirect to, the noise S5

    kubectl get pods -n astronomy-shop showed one Ready ad Pod and one new ImagePullBackOff ad Pod. The next checks targeted the checkout dependency rather than ad.

  4. Configuration comparison identified the wrong endpoint S6–S8

    kubectl get svc showed Product Catalog on 8080. kubectl describe deploy checkout showed PRODUCT_CATALOG_ADDR=product-catalog:8082; describing Product Catalog confirmed its 8080 service port.

  5. The agent repaired checkout S9–S11

    kubectl set env deploy/checkout -n astronomy-shop PRODUCT_CATALOG_ADDR=product-catalog:8080
kubectl rollout status deploy/checkout -n astronomy-shop --timeout=60s

    The environment update and rollout-status command succeeded.

  6. Recent trace queries still contained 8082 failures S12–S15

    After waits and a rollout check, the agent queried checkout traces again. Those results still included 8082 timeout spans. A recent trace window can include requests from before the new Pod served traffic, so this alone does not prove the repair failed.

  7. The new Pod already showed the correct address S16–S19

    kubectl describe pod checkout-c4dfb95f-fzksm reported PRODUCT_CATALOG_ADDR: product-catalog:8080. The agent then read checkout logs, waited, and requested more traces; the trace result still contained 8082 errors.

  8. Two environment rechecks failed at the tool boundary S20–S21

    The safe kubectl tool rejected a piped printenv | grep command. A direct kubectl exec ... -- printenv returned exit code 127. Neither failure refuted the successful Pod description from S16.

  9. The agent added an unnecessary Service port S22

    kubectl patch svc product-catalog -n astronomy-shop --type='json' \
  -p='[{"op":"add","path":"/spec/ports/-","value":{"name":"grpc","port":8082,"targetPort":8080,"protocol":"TCP"}}]'

    The tool returned service/product-catalog patched. The saved trajectory ends here, with no agent-side test of that patch and no final submission. The driver later passed both oracles, but the evidence does not show that adding the extra port was needed.

Noise run 2 · 1003_2053

120.300 s · Target pass · Main oracle pass

This was the fastest run. The agent saw the ad Pod failure in the Pod list, verified the Product Catalog port mismatch, changed only checkout, and submitted the checkout diagnosis.

  1. Preflight preserved the checkout fault

    The bad ad Pod was in ImagePullBackOff while the original ad Pod remained Ready. Checkout's failure ratio measured about 1.001 before and 1.000 after injection. The target alert kept firing and all recorded Service endpoints were unchanged.

  2. Initial telemetry linked checkout to Product Catalog S3–S4

    The agent requested services, checkout operations, checkout traces, and a dependency graph. A checkout GetProduct span showed an 8082 dialing timeout.

  3. Pod listing showed the separate ad failure S5

    kubectl -n astronomy-shop get pods -o wide listed the new ad Pod in ImagePullBackOff. The agent did not issue an ad repair command.

  4. Three configuration checks resolved the port mismatch S6–S8

    The checkout Deployment exposed PRODUCT_CATALOG_ADDR=product-catalog:8082; the Product Catalog Deployment and Service YAML exposed port 8080, with the Service mapping port: 8080 to targetPort: 8080.

  5. Checkout was changed to the real port S9–S10

    kubectl -n astronomy-shop set env deployment/checkout PRODUCT_CATALOG_ADDR=product-catalog:8080

    The update succeeded, and the agent waited 20 seconds.

  6. Follow-up checks confirmed the new configuration S11–S14

    A 10-minute trace query still included 8082 failures. The next Deployment description showed product-catalog:8080, and the checkout Pod inspection also reported that address. The later 5-minute trace could still include pre-repair requests.

  7. Traffic checks were inconclusive on their own S15–S18

    The agent queried frontend and checkout traces, waited, then queried a five-minute checkout HTTP count metric. The metric returned an empty vector. That empty result is not proof of alert clearance.

  8. The agent submitted the diagnosis; driver verified recovery S19 + driver

    The submission identified the 8082/8080 mismatch and the checkout environment-variable fix. After the agent run, the driver observed 120 seconds without the matching alert and the benchmark's Product Catalog oracle passed.

Noise run 3 · 1003_2121

214.881 s · Target pass later · Main oracle pass

This run shows why agent observation and final scoring must be separated. The agent repaired the checkout address, but its last alert query still found the assigned alert firing. The driver allowed the rate window to clear and then verified sustained silence.

  1. Preflight confirmed non-interference

    The new ad Pod was waiting in ImagePullBackOff, the old ad Pod was Ready, and checkout's failure ratio remained near 1.000 → 1.001. The target alert was firing both before and after noise injection; all recorded endpoints were identical.

  2. The first checkout trace exposed the timeout S3–S4

    After listing services, the agent called get_traces(service="checkout", last_n_minutes=15). A Product Catalog GetProduct span reported :8082: i/o timeout.

  3. Pod check also exposed the ad noise S5

    kubectl get pods -n astronomy-shop -o wide included a new ad Pod with ImagePullBackOff. Investigation continued with checkout and Product Catalog, not ad.

  4. Service and Deployment checks showed the mismatch S6–S8

    The Product Catalog Service listed 8080, checkout's PRODUCT_CATALOG_ADDR was 8082, and the Product Catalog Deployment exposed 8080. This directly explained the trace's attempted 8082 connection.

  5. The agent changed only checkout S9–S11

    kubectl set env deployment/checkout -n astronomy-shop PRODUCT_CATALOG_ADDR=product-catalog:8080
kubectl rollout status deployment/checkout -n astronomy-shop

    The update and rollout-status call succeeded.

  6. Configuration looked repaired while trace windows still contained errors S12–S17

    A new Deployment description showed product-catalog:8080. The agent examined checkout Pods and several short trace windows; some still contained 8082 failures. Such results can overlap the pre-repair interval and cannot alone establish a continuing failure.

  7. Logs and another trace preceded the decisive alert check S18–S20

    The agent read checkout logs, waited 30 seconds, and queried a two-minute checkout trace window. The saved S20 observation did not show the earlier 8082 timeout text, but a trace query is not equivalent to alert-state verification.

  8. The assigned alert was still firing when the agent checked S21

    get_metrics('ALERTS{alertname="HighRequestErrorRate"}') returned a firing time series with method=POST, name=/api/checkout, and namespace=astronomy-shop. This is an explicit agent-side observation, not a failed final score.

    At S21, HighRequestErrorRate{method="POST",name="/api/checkout"} still had alertstate="firing".

  9. The agent waited; the driver verified the eventual clearance S22 + driver

    S22 waited 60 seconds. The saved trajectory ends without a final f_submit_tool call. The driver then used its 240-second recovery allowance and required 120 seconds of silence; both the targeted alert oracle and the benchmark mitigation oracle passed.

6. Interpretation and limits

What the runs show: All six agents found a repair consistent with the intended checkout fault. The three noise agents encountered the bad ad Pod in a general Pod listing but did not issue an ad repair. The noise mechanism produced an independent alert while the preflight gate confirmed the checkout failure and the relevant endpoints persisted.

What deserves attention: Noise run 1's extra Service port is a real mitigation side effect. Its sequence is especially notable because S16 had already shown the repaired checkout Pod's 8080 address. The available runs do not establish that ad noise caused the extra patch. Noise run 3 illustrates alert delay: the agent saw firing, while the driver later observed the required sustained clearance.

What the data cannot establish: With three runs per arm, the observed 3/3 success in both arms and agent-time medians of 141.653 seconds (control) versus 176.700 seconds (noise) do not support a stable success-rate or speed effect. Pairwise noise-minus-control time differences were +42.981, −21.353, and +59.485 seconds.

Reading the oracle logs: Their pass message says “no firing alerts detected in namespace.” The checkout experiment instantiated the weak oracle with exact matching labels, so that generic log phrase refers here to the assigned HighRequestErrorRate, not to every alert in the namespace.
