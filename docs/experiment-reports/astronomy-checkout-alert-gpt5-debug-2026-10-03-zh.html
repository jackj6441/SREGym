独立噪声

ad 现有 Ready Pod＋新 Pod ImagePullBackOff

噪声组把 ad Deployment 的新镜像指向不存在的版本，使新 Pod 拉取失败并触发另一种告警 PodStatusError；旧的 Ready ad Pod 保持服务。噪声在 agent 启动前注入。

目标判定只匹配 HighRequestErrorRate、method=POST、name=/api/checkout。PodStatusError 不要求 agent 修复；三次噪声注入都通过了真实流量和端点不干扰检查。

调试结论与边界

已观察到：六轮 agent 都自行把 checkout 依赖地址改回 product-catalog:8080；三轮有 ad 噪声时，agent 都在 Pod 列表中看见异常 Pod，但没有改动 ad。三轮噪声的主故障不干扰 gate 均通过。

值得复查：噪声 1 在主修复后增加 8082 Service 端口。这是额外变更，不属于预期的最小修复；现有结果无法证明它是噪声导致的。噪声 3 在 agent 查询时告警仍 firing，driver 后续通过恢复宽限期与持续静默检查才给出成功。

不能推断：三轮每组不足以估计噪声对成功率或耗时的因果影响，也不能把所有 agent 的提交文字或空指标结果当作最终验证。最终成功由定向弱 oracle 与 benchmark 主 oracle 共同支持。

实验口径与来源

  • 六轮按对照 1、噪声 1、对照 2、噪声 2、对照 3、噪声 3 顺序运行；Stratus mitigation 模型 gpt-5，judge gpt-4o-mini，每轮 agent timeout 1800 秒。
  • 弱 oracle 在 agent 结束后定向匹配 HighRequestErrorRate / POST / /api/checkout，允许最多 240 秒恢复，再要求 120 秒不 firing。日志里的“no firing alerts in namespace”是通用文案；本实验的代码按目标标签过滤。
  • 先前一轮用于校准告警等待时间，已中止且不计入六轮正式结果。正式结果汇总：实验 Markdown 报告；机器可读汇总；oracle 日志摘录。
  • 时间线只保留关键步骤，S 编号可在各轮原始 trajectory.json 中核对。preflight 数据来自各轮 noise_evidence_attempt1.json。本页面可离线打开，无外部脚本或网络依赖。
