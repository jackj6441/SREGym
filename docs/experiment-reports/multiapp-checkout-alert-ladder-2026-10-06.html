五应用、多故障告警实验报告

SREGym · CloudLab · 2026-10-06 · GPT-5 / Stratus · 每个条件一次正式运行

结果：1 到 5 个并发故障的五轮正式运行中，agent 均修复了指定的 Astronomy Shop HighRequestErrorRate。第 4 轮还做了一项不必要的 Product Catalog Service 修改。每个条件仅运行一次，因此这里记录的是观察结果，不能据此估计成功率或趋势。

实验设置

每轮都重新部署 Astronomy Shop、Hotel Reservation、Social Network、Fleet Cast、Blueprint Hotel Reservation。主故障固定为 checkout 的 PRODUCT_CATALOG_ADDR=product-catalog:8082；正常端口是 8080。目标只包括 HighRequestErrorRate{namespace="astronomy-shop",method="POST",name="/api/checkout"}。

给 agent 的最后一句任务原文是：

“Astronomy Shop has a firing HighRequestErrorRate alert for POST /api/checkout. Investigate and resolve this alert.”

提示词没有透露端口故障、根因或额外故障。每轮在 agent 启动前确认主告警和每个新增告警都已 firing；checkout 持续失败、两个 cart 对照接口健康，且 Astronomy 主路径 Service endpoints 不变。预检失败的尝试不算 agent 失败。

方法与成功判定

五轮使用同一台 CloudLab Kubernetes 节点、相同的五应用部署范围和 full workload profile。Astronomy 使用应用自带负载生成器；Hotel 与 Social 还启动 wrk2 负载（配置为 rate=10、connections=10、duration=30、threads=2）。每轮从清理后的集群开始，累加固定顺序的 1、2、3、4 或 5 个故障；预检通过后运行一次 GPT-5 Stratus mitigation agent，最多 20 轮，agent 超时设置为 1200 秒。网络访问模式为 filtered。

第 1 轮 · 1 个故障 · 413.1 秒

只有 checkout 端口故障；预检确认目标告警 firing、checkout 失败率 98.5%、cart 对照正常。该轮是后续噪声轮次的参照。

  1. #3–12 Agent 先查服务、依赖图、checkout/frontend 的 Jaeger trace 与 Prometheus 指标，没有收到端口根因提示。
  2. #13–18 检查 Pods、日志、Service 与 endpoints。kubectl get endpoints -n astronomy-shop checkout cart product-catalog 显示 Product Catalog 仍有 8080 端点，排除了“Service 没有后端”这一解释。
    checkout          10.244.149.120:8080
cart              10.244.149.19:8080
product-catalog   10.244.149.60:8080
  3. #19–21 对比三个 Deployment；kubectl describe deploy/checkout 显示错误地址：
    PRODUCT_CATALOG_ADDR: product-catalog:8082
  4. #22 执行 kubectl set env deploy/checkout -n astronomy-shop PRODUCT_CATALOG_ADDR=product-catalog:8080，工具返回环境变量已更新。
  5. #23 到达 20 轮上限后由驱动自动提交。轨迹中没有 agent 自己的修复后告警查询；外部结果记录 Mitigation.success=True、TTM 413.1 秒。

本轮观察：agent 花较多轮次定位配置，最终只改 checkout；成功依据主要是外部判定。

  5. #16–19 查询告警、等待告警计算窗口，并对精确目标标签再次查询，结果为空向量，然后主动提交。

第 3 轮 · 加入 Hotel Service 无端点 · 350.3 秒

Host 预检确认 Hotel recommendation 有 Ready Pod，但 Service selector 错配、没有 endpoints，ServiceEndpointDown firing；Astronomy 的目标和 ad 告警也仍 firing。

  1. #3–5 Agent 查看 Astronomy Pods 和 checkout trace；新 ad Pod 为 ImagePullBackOff，旧 ad Pod Ready。轨迹中没有去 Hotel 查询 selector。
  2. #6–9 查询 Astronomy Service、checkout/Product Catalog Deployment 与 checkout 日志。describe deploy checkout 显示 PRODUCT_CATALOG_ADDR: product-catalog:8082。
  3. #10–13 更新 checkout 地址到 8080，等待并看到新 checkout Pod Ready；没有修改 Hotel Service。
  4. #14–16 两次尝试在 Pod 内运行 printenv，一次因管道命令受限、一次因容器中命令不存在而失败；随后 kubectl describe deploy checkout 确认新配置。

本轮观察：Hotel 的无端点告警未把 agent 引向其它应用；修复后验证过程有工具命令失败，成功结论以外部目标判定为准。

分析与判读边界

观察到的行为：五轮有效运行均修复了指定 checkout 告警，TTM 在 332.0–413.1 秒之间，没有随故障数单调增加。第 1、2、3、5 轮只改 checkout；第 4 轮虽然成功，还额外改了 Product Catalog Service。Agent 在多轮 Pod 列表中看到 ad 错误 Pod，却没有将它当成修复目标；Hotel 和 Social 的故障也未被修复。

  • 每个故障数只有一次有效运行，固定顺序也没有随机化。五次成功说明这组具体条件下未观察到目标修复失败，不能估计总体成功率或证明增加故障没有影响。
  • agent 提示词明确给出 Astronomy Shop、HighRequestErrorRate 和 POST /api/checkout，这有助于限定调查范围；本实验不能单独衡量在没有明确目标时的多告警分诊能力。
  • checkout 预检请求率约 0.019–0.066 rps，低流量下两分钟 rate 波动明显。第 5 轮采用连续两次通过采样，而前四轮是单次快照；虽然数值门槛相同，预检流程并非完全一致。
  • Blueprint Hotel Reservation 已部署，但此版本 workload 方法为 no-op，没有增加请求流量。第 2 轮还出现与任务无关的 TiDB 误报告警，规则在第 3 轮前修正；这些条件限制了轮间比较。
  • 成功指标只要求目标告警和主故障 oracle 恢复，不惩罚多余修改。第 4 轮说明应另行审查变更范围与副作用。

环境与清理：为了让五应用共存，CloudLab 节点根分区从约 64 GiB 扩至约 216 GiB，kubelet maxPods 从 110 调至 200；这两项宿主机配置仍保留。正式实验结束后，五个应用命名空间均已删除，节点为 Ready、根分区剩余约 163 GiB。

  .venv/bin/python main.py --problem multiapp_checkout_alert_N \
  --stages mitigation --profile full --agent stratus --model gpt-5 \
  --agent-timeout 1200
